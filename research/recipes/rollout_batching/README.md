# Fixed-network rollout batching

This recipe measures actual Rust Go/MCTS rollouts with a fixed neural network and a fixed set of games. It varies inference batching or dispatch without introducing extra games, a different search budget, or a learner.

`serial` waits for each microbatch. `async` submits the same microbatch executable repeatedly before retrieving results. `scan` evaluates those microbatches through `jax.lax.map` in one compiled device loop. `wide` compiles one wide batch and can compare its outputs against serial microbatches on identical pending positions. The [JAX map documentation](https://docs.jax.dev/en/latest/_autosummary/jax.lax.map.html) describes the compiled mapping primitive; it does not promise identical floating-point lowering across execution forms.

The CPU configurations qualify the mechanism on 32 games. The TPU configurations use the same 1,024 games and 32 pinned native workers on each of four hosts; inference batches are 128, 256, 512, or 1,024 positions per host. Each TPU chip receives one quarter of that batch. Model weights come from the pinned ownership pilot, including its model implementation and observation/scoring contract. This is a throughput benchmark, not a Go-strength or learning experiment.

JAX starts under CPU affinity 0–15, and native workers run on 16–47. The pod launcher therefore needs `--controller-cpus 64`. The report records observed per-thread affinity masks and process CPU time. JAX compilation and a fixed warmup precede measurement. Forward calls use a host-local device mesh; only the start/end barriers involve other hosts. Every model response still passes through the authoritative native search.

First run configurations with `verify_trace: true`, then use the frozen `compare.py` on both artifact directories (`--hosts 4` for pod attempts). Requests, training targets, completed game records, actor actions, unfinished rows, and RNG states must agree exactly. Diagnostic unfinished-row root values may differ by at most 1e-5 because batch shapes can change floating-point code generation. `verify_outputs: true` additionally runs serial reference inference on every pending batch and retains the first numerical discrepancy as an NPZ fixture. Reference inference has separate work counters and time. A trace difference fails exact-equivalence qualification and must be investigated. It does not by itself establish a model-quality regression. Verification includes warmup, while work/timing counters exclude it.

Trace hashing is CPU work and appears separately in the report. A timing study must first pass trace qualification, then register repetitions with both verification flags disabled and otherwise matching configuration. `measure.py` verifies these contracts, executes bounded counterbalanced repetitions, and checks every native useful-work counter. Compare the slowest host per attempt, retain failed attempts, and report both inference time and the complete measured segment. Compiler cost estimates are diagnostics; they do not establish model FLOP utilization. Runtime affinity reports show that some libtpu threads broaden their CPU masks after initialization; starting JAX under an affinity does not guarantee all runtime threads remain inside it. Any later change to game count, search scheduling, or model changes the experiment and needs a separate comparison.

The measured asynchronous variant preserved all tested TPU outputs and complete traces, then delivered a median 1.1812× complete rollout speedup across three repetitions. This missed the registered 1.20× systems-screen threshold. Wide and scanned variants produced different numerical outputs and traces and require separate approximate-execution validation. Complete protocols and reports are in `research/studies/rollout_batching/`.
